# 业务知识定义 v1.0.0

本步骤交付18个指标、6类政策、13个字段释义，以及可用于RAG的24条自包含知识。对应 `retail_eval_v1` 的已验收快照，不修改数据库，不执行付费模型调用。

## 设计依据

1. **源数据事实**：UCI https://doi.org/10.24432/C5CG6D 说明价格单位为英镑、C前缀发票为取消、存在缺失值。它不提供本项目的销售额、复购率等统一指标定义。
2. **已验收数据快照**：上一步验收报告确认字段、记录数、日期范围和缺失情况。客户缺失243007条，因此客户类指标必须约束分子和分母范围。原始日期截至2011-12-09，因此2011-12不能默认当完整月进行环比。
3. **本项目场景选择**：销售正向记录使用非取消、正数量、正单价；保留匿名销售、采用期间内复购、空SUM返回NULL等规则，是为可复现实验明确制定的约定，不宣称是所有企业的通行标准。
4. **SQL可执行与可核验性**：每个指标都有明确范围、粒度、公式、单位、缺失策略和依赖。用同一快照上的独立Decimal计算与MySQL结果对比，避免只靠语言描述判断一致性。

## 核心取舍

| 问题 | 冻结的选择 | 原因 |
|---|---|---|
| 什么算有效销售 | is_cancelled=0 AND quantity>0 AND unit_price>0 | 区分正向销售、取消、盘点/调整等记录，不发明支付状态 |
| 匿名销售 | 计入销售额，排除客户类指标 | 缺失客户不代表销售不存在；避免分子包含匿名销售却除以已知客户数 |
| 客单价 | 不作为自动别名；区分平均订单金额与每购买客户平均销售额 | 两个分母合理但不同，需要明确选择 |
| 复购 | 同一期间每客户不同销售发票至少两张 | 同发票多明细不等于复购；不是跨期留存 |
| 商品标识 | stock_code，不按description | 商品名可变且可缺失 |
| 取消金额 | C前缀全部有符号金额 | 不从取消编号猜原订单，不当作已支付退款 |
| 时间 | 明细时间，左闭右开；不做时区换算 | 来源无时区；避免结束日漏数和发票金额跨期搬移 |
| 完整月份 | 2009-12至2011-11 | 只说明日历覆盖，不保证每日有交易 |
| 没有数据 | COUNT=0，SUM和无法定义的比率=NULL | 区分“确实是零”与“没有可聚合值” |
| 精度 | 中间计算不按展示位数舍入 | 避免月度/份额累计舍入误差 |
| 去重 | 源行不去重，客户/发票按定义去重 | 保留可追溯原始事实 |
| 分组汇总 | 客户数/发票数不可随意跨组相加 | 同一客户或发票可能出现在多个国家/商品组 |

## 文件与用途

- `contract-v1.json`：唯一权威定义，含版本、快照哈希、指标ID、公式、规则和依据。
- `指标字典-v1.md`：便于人工审阅的中文说明。
- `rag-documents-v1.json`：24条可召回知识，只有定义，不含题目、参考SQL或查询数值。
- `freeze-v1.json`：定义、导出文件、验证器与测试的SHA256。修改定义必须发布新版本并重新验收。
- `../validate_knowledge.py`：私有确定性验证器。不可上传到Agent知识库。
- `.vscode/retail-eval/knowledge-validation.json`：本地完整数值核验报告。不可上传到Agent知识库。
- `../reports/knowledge-acceptance-2026-10-17.json`：不含逐题/逐指标答案的验收摘要。

知识条目采用固定指标ID而不是题号。每条指标包含共同过滤、时间、单位、空值规则和必要依赖，避免只召回一个指标时缺少关键前提。需要澄清的词不与明确指标共用自动别名。

## 核验方式

```bash
# 定义结构、字段引用、ID和别名冲突校验
python3 tools/retail_eval/knowledge.py validate

# 边界样例与原数据层测试
python3 -m unittest discover -s tools/retail_eval -p 'test_*.py' -v

# 只读MySQL核验：完整期间、2011年6月、空期间，各18指标
python3 tools/retail_eval/validate_knowledge.py
```

核验器先验证参考明细哈希与冻结快照一致，再用源端Decimal独立计算，与MySQL SQL结果逐项比较。除法误差上限1e-6（MySQL固定精度除法），空值严格匹配。后续正式题目可制定更精细的逐指标比较容差。

人工可计算的边界样例覆盖：同发票重复商品、变动单价、缺失描述、匿名与空白客户、取消与负数量、零价格、精确月份边界、没有匹配记录、零分母。它们是规则测试，不计入后续500道正式题。

## 与现有业务知识接口对接

现有 `POST /api/business-knowledge` 的请求字段为 businessTerm、description、synonyms、isRecall、agentId。生成某个智能体的请求列表：

```bash
python3 tools/retail_eval/knowledge.py export --agent-id 123 \
  --out .vscode/retail-eval/business-knowledge-agent-123.json
```

把123替换为实际智能体ID。导出的JSON是请求数组，需要逐条POST，当前接口不是批量接口。默认导出的rag-documents保留knowledgeId用于版本追溯；指定agent-id后会移除额外字段，生成符合DTO的请求体。此命令只导出，不发送、不向量化。实际导入会触发应用的Embedding流程，应在之后接入阶段执行并记录远端ID与知识ID映射，避免重复导入。

本次只固定定义与导出文件，尚未修改应用知识库；第三步的问题、答案、评分器也尚未建立。

## 为OFF/ON对照保留边界

- ON：从此版本的业务知识文档检索后注入Evidence。
- OFF：不接收这些指标、政策文档或等价定义。
- 两组都保留物理字段与逻辑关联；不要把销售/复购公式复制进共享Schema注释或共享系统提示词。
- 此次知识包没有官方标准答案或评测数值。Agent可见定义，评测端可见验证器与结果。

## 冻结与改版

v1.0.0定义必须先于正式题集冻结。公式、过滤、时间、空值或别名语义变化，应建立新版本、重新导出、重新验证、重新冻结；不能在看到ON/OFF成绩后静默改参考口径。
